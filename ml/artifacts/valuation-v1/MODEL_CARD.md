## Data

- Source: `data/raw/Transaction data for valuation.xlsx`, sheet `Sheet1`.
- Period: **2026-01-01 to 2026-08-31 (8 months)**. "Today" for indexing purposes =
  the latest month in the data = **August 2026**.
- 5,000 raw rows -> 4,991 after cleaning (`ml/cleaning.py`): 1 exact duplicate row
  dropped, 8 rows with a missing target (`price_per_sq_meter`) dropped. See
  `ml/cleaning.py`'s module docstring and `ml/tests/test_cleaning.py` for every
  cleaning rule and its rationale; the exact per-rule row counts from the last
  training run are in `metadata.json` -> `cleaning_report`.
- Area (`omrade`, task 4b): 4,395 of 4,991 rows (88.1%) join to a mapped area via
  `data/derived/postnummer_omrade.csv`; the remaining 596 rows (12%, postcode not in
  the mapping — see `ml/mapping/README.md`) get the category
  `"Okänt (postnummer ej kartlagt)"` rather than being dropped or guessed. This
  category consistently has the worst per-area MAPE of any group (21-24%, vs 8-18%
  for mapped areas) — concrete evidence that the 4b mapping is doing real work.
- **`utgångspris` is not a column in this file and was never used.** (It lives only
  in the second workbook, used for task 5, which is a different, unrelated
  prediction target — bid-vs-contract-price spread, not valuation.)

## Features

| Group | Features |
|---|---|
| Numeric | living_area, number_of_rooms, apartment_floor_clean, building_storeys_clean, build_year_clean, monthly_fee_clean, fee_per_sqm (=monthly_fee/living_area), month_num (1-8, time feature) |
| Missing indicators | apartment_floor_missing, building_storeys_missing, build_year_missing, monthly_fee_missing |
| Categorical | omrade (14 levels incl. "Okänt"), elevator_clean (ja/nej/okänt), balcony_clean (ja/nej/okänt) |

Numeric features are median-imputed (fold-safe, imputer fit only on the training
split of each fold/split) plus standardised for the linear model; missingness is
additionally captured as its own binary feature so the imputation cannot hide an
informative missing pattern (e.g. `build_year_missing` has a large, significant
negative effect — see the effects table — meaning "build year unknown" rows are
systematically different, most likely newer/off-plan sales where the year had not
propagated into the source system yet).

**Time**: a numeric `month_num` (1-8) feature is used, rather than one-hot month
dummies, because with only 8 months of data a linear month trend is a reasonable,
low-variance way to let every model (including the tree ensembles) pick up
month-over-month drift; the interpretable OLS companion model (used for the effects
table, not for production predictions) reports `month_num`'s coefficient as a %
effect per calendar month, which is the closest thing to a price index this design
produces (+0.32%/month, 95% CI -0.01% to +0.65%, p=0.054 — not quite significant at
5%, i.e. we cannot confidently distinguish a month-over-month drift from noise in 8
months of data). No separate "index" step was applied to historical prices before
training; the model conditions on `month_num` directly instead.

## Log vs level (target transform)

Compared with the ridge baseline, 5-fold CV, MAPE on TOTAL price:

| Target | MAE (SEK) | MAPE |
|---|---:|---:|
| log(price_per_sqm) | 938,700 | 20.00% |
| price_per_sqm (level) | 922,067 | 20.78% |

Log wins on MAPE (the metric the brief asks to optimise/report) despite a very
slightly higher MAE; log is also the standard choice for right-skewed price data and
guarantees positive predictions, so **log(price_per_sqm) is used for every model**.

## Chosen model & justification

**LightGBM**, chosen by: take the model with the best CV MAPE (LightGBM, 13.27%);
of the models within **1.0 percentage point** of that (LightGBM 13.27%, XGBoost
13.43% — both within margin; Random Forest 15.09% and the linear model 20.00% are
not), pick the simplest. LightGBM and XGBoost are treated as roughly equally
"simple" (both gradient-boosted tree ensembles); LightGBM is picked as the
marginally better and first-considered of the two. The linear model is **not**
competitive here (6.7-7.6 percentage points worse MAPE on CV and time-split
respectively) — the relationship between the features (especially area and floor)
and log-price is evidently not well captured by a linear-in-features model even with
one-hot area dummies, so the "small margin" rule correctly rules it out rather than
forcing a simplicity trade-off that would cost real accuracy.

**Caveat**: choosing LightGBM has a real serving-complexity cost — see "Serving
recommendation" below. If frontend-only serving (coefficients evaluated in
TypeScript, no backend call) is a hard product requirement, the regularised
log-linear model is the fallback, at a cost of roughly +6-7 percentage points MAPE.

## Prediction intervals

Method: split conformal, on the absolute residual of TOTAL price (symmetric
interval: `[pred - q, pred + q]`, `q` = the empirical `(1-alpha)`-quantile of
absolute calibration residuals; `alpha = 0.10` for a nominal 90% interval).

**Honest, out-of-time coverage check** (this is the number to quote): model trained
on Jan-Jun only, `q` calibrated on a held-out 20% slice of Jan-Jun, then evaluated
for coverage on the untouched Jul-Aug test set (n=888):

- Target coverage: 90%
- **Empirical coverage: 85.1%** (q = ±1,432,511 SEK on total price)

The interval is a bit too narrow / under-covers relative to the 90% target when
evaluated genuinely out-of-time — flagged as a known limitation, not silently
rounded up. This is plausible with only 8 months of data and a period that includes
a genuine within-year price drift the calibration fold may not fully capture.

The **shipped production artifact** (`model.joblib`, fit on all 8 months) instead
calibrates `q` on a random (not time-based) 20% holdout of all rows, since it is
trained on all available months: q = ±1,684,419 SEK. This number has **not** been
validated out-of-time (there is no more recent unseen data to test it against) and
should be treated as provisional until re-checked against September 2026+ data once
available.

## Two models, one purpose

This artefact ships **two** fitted objects that answer two different questions:

1. **`model.joblib`** (LightGBM pipeline, production predictions) — best accuracy,
   not directly interpretable feature-by-feature.
2. **`coefficients.json`** (unregularised OLS on the same features) — not used for
   predictions (its CV/time-split MAPE, ~20-23%, is meaningfully worse than
   LightGBM's), used only to answer "what does changing X do to price, all else
   equal" with a confidence interval, which a tree ensemble does not give you
   directly. This split (accurate black-box model for prediction + a separate glass-box
   model for explanation) is a standard, documented trade-off, not an oversight.

## Serving recommendation (recommendation only, not implemented)

- **Chosen model is LightGBM**, which cannot run as plain coefficients evaluated in
  TypeScript in the frontend bundle — it needs either (a) a backend endpoint that can
  load `model.joblib` (Python) or an exported/portable format (e.g. ONNX, or
  LightGBM's own `Booster.save_model()` text format re-implemented/loaded by a small
  Python service), or (b) accepting the accuracy cost of shipping the linear
  fallback's coefficients JSON directly to the frontend.
- **Recommendation: serve from a backend endpoint**, not the frontend bundle, for
  three reasons: (1) the winning model literally cannot be evaluated client-side
  without an ONNX/JS port, so frontend-embedded coefficients is not available for the
  best model; (2) a backend endpoint can be updated (retrained artefact swapped in)
  without a frontend deploy, matching Binfo's existing pattern of server-side model
  logic (`src/server/`); (3) it keeps the ~1.1 MB model file and every row of
  training data fully off the client, consistent with CLAUDE.md's "never make raw
  rows reachable from the frontend bundle" rule (the model itself is a derived
  aggregate, not raw rows, but keeping it server-side is still the simpler, safer
  default).
- If product/eng later decides simplicity beats the ~6-7pp MAPE gap, the fallback is
  to ship only the log-linear model's `coefficients.json`
  (`effects_pct_all_else_equal` + area dummies + intercept) to the frontend and
  evaluate it there — speed and update-ease are then both excellent (no network
  round-trip, but every price update requires a frontend deploy instead of a backend
  data refresh).
- This recommendation is **not implemented** — no frontend or backend serving code
  was touched, per the task brief (ml/ and data/derived/ only).

## Limitations

- Only 8 months of data (Jan-Aug 2026); the "time index"/month effect is not
  statistically significant at 5% (p=0.054), so seasonal/trend adjustment beyond what
  `month_num` already captures should be treated as low-confidence.
- 12% of rows (596/4,991) have no mapped area (`Okänt`) and consistently get the
  worst per-area MAPE (21-24%) — closing the 4b mapping gap (see
  `ml/mapping/README.md` limitations) is the highest-leverage next step for accuracy.
- Prediction interval under-covers on the honest out-of-time check (85.1% vs 90%
  target) — treat the stated interval as indicative, not calibrated to spec.
- `build_year`, `apartment_floor`, `building_storeys` all have substantial raw
  missingness (9-26%) resolved by median imputation + a missing-indicator flag, not
  by a more sophisticated imputation model; a few of the missing-indicator effects
  are themselves large (build_year_missing: -10.45%) and worth investigating rather
  than taken at face value — they may be proxying for something else (e.g.
  new-construction/off-plan sales) rather than pure missingness noise.
- Area effects for `Centrala Stockholm` (n=12 in this training sample) are very
  noisy; do not trust that estimate without more data.
- LightGBM/XGBoost were assumed unavailable per the task brief (based on the global
  Python environment) but installed successfully in `ml/.venv` from PyPI (internet
  access was available in this environment) — see `ml/requirements.txt`. If the
  target deployment environment genuinely cannot install them, fall back to Random
  Forest (next-best, 15.09% CV MAPE, pure scikit-learn) or the linear model.
