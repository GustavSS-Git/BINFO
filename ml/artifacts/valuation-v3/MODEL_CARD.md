## 1. Feature set and inference (Stockholm municipality)

Inputs: `boarea`, `antalRum`, `manadsavgift`, `vaning`, `byggar`, `hiss`, `balkong`,
`postnummer`, `omrade` (from `postnummer_omrade.csv`, "Okänt (postnummer ej kartlagt)" if unmapped).

Booster input vector, in `model.json.feature_order_out` order:

```
num__living_area, num__number_of_rooms, num__apartment_floor_clean, num__build_year_clean,
num__fee_per_sqm, num__postcode_delta,
ind__apartment_floor_missing, ind__build_year_missing, ind__monthly_fee_missing,
cat__omrade_* (14 one-hot), cat__elevator_clean_{ja,nej,okant}, cat__balcony_clean_{ja,nej,okant}
```

**Exact inference formulas (what the TypeScript side must implement)**

1. `fee_per_sqm = manadsavgift / boarea`, or missing if `manadsavgift` is missing.
2. `postcode_delta = table[postnummer]` from `postcode_encoding.json` (`table` is
   postnummer → number); **0.0 if the postnummer is missing or not in the table** (that is also
   what the model saw during training for postnummer with no other sales, see below).
3. Missing numerics (`antalRum`, `vaning`, `byggar`, `fee_per_sqm`) → the median in
   `numeric_medians_for_imputation`. Indicators: `apartment_floor_missing` = 1 iff `vaning` missing,
   `build_year_missing` = 1 iff `byggar` missing, `monthly_fee_missing` = 1 iff `manadsavgift` missing.
4. One-hot: `omrade` (missing → `categorical_fill_value_for_imputation.omrade`),
   `hiss`, `balkong` (`ja|nej|okant`; unknown categories → all zeros).
5. `log_ppsm = Σ_trees leaf(x)` — LightGBM dump format, go left iff `x[split_feature] <= threshold`,
   as in v2. (Python/LightGBM-native vs the exported, 6-significant-figure-rounded booster:
   max |Δ log price| = 4.8e-05 on the first 200 rows.)
6. `pris = exp(log_ppsm) × smearing_factor × boarea`, `smearing_factor` =
   `metadata.production_model.smearing_factor` = **1.004473**.
7. Interval: `pris × exp(±q)`; `q` = `conformal_interval_evaluation.q_per_area_log[omrade]`,
   fallback `q_overall_log` (0.2161) — identical to v2.

`ml/tests/test_valuation_v3.py` contains a ~30-line Python reference implementation of 1–7 that
reproduces all 52 `parity_fixtures.json` rows to 1e-9; port that.

### `postcode_delta` — definition

Target encoding of `postal_code_clean`, shrunk toward the omrade level:

```
v_i      = log(price_per_sqm_i) − mean over training rows in the same omrade of log(price_per_sqm)
delta[p] = Σ_{i in p} v_i / (n_p + k)            (= n_p/(n_p+k) × (postnummer mean − omrade mean))
k = 0.5, mode = "raw"
```

- **No leakage.** The booster is trained on *out-of-fold* deltas (5 inner folds, seeded; a row's
  delta never uses its own price; a postnummer with a single sale gets 0 out-of-fold). Every
  CV fold and the Jul–Aug split recompute the encoder from the training part only.
  Inference uses the full-data table (632 postnummer in Jan–Jun; the shipped table is fit on
  all 8 months, `postcode_encoding.json`, 13 KB, rounded to 6 d.p., fixtures use the rounded table).
- Selection: grid k ∈ {0.5, 1, 2, 3, 5, 10, 30} × mode ∈ {raw, resid} on Jan–Jun 5-fold CV
  (n=4,103): raw k=0.5 best at 10.17 % vs 12.42 % without; "resid" (encoding the out-of-fold residual of
  the no-postcode model) was worse at every k (10.64–10.80 %). The best k is at the edge of the grid
  (smaller k was not tried; k=1 is only 0.03 pp worse).
- Held-out Jul–Aug: **10.18 % vs 12.63 % (n=888, gain 2.45 pp)** with default params.
- Where it helps and where it does not (Jul–Aug): postnummer present in the Jan–Jun table:
  n=857, MAPE 9.91 % with vs 12.55 % without. **Postnummer not in the table: n=31, 17.86 % with vs
  15.07 % without** — the model treats them as an average postnummer in the area; n is small, but
  an unseen postnummer is a reason for lower confidence.
- Interpretation: the postnummer is close to a building/block identifier; this is most plausibly
  genuine local signal, not a leak (the gain holds on strictly later months), but part of it is
  repeat sales in the same building/BRF in the data, which will not exist for a BRF the product has
  never seen. The table has 632 postnummer for 4,103 rows (≈6.5 rows each), so most entries are
  based on few sales — **do not present a single postnummer's delta as a market statistic**.

## 6. Regional method (outside Stockholm municipality)

Owner principle: the apartment's characteristics say how it differs from the local average; the
municipality average sets the baseline.

```
kr/m² = A × r(x)         A = kommun 12-month average (inside Stockholms län, outside 0180)
                         A = national average 46 317 kr/m² (outside the län)
pris  = kr/m² × boarea   interval: pris × exp(±q_regional)
```

**r(x) design — and a design decision that deviates from the brief's example.** The brief suggested
`r = exp(g)·smear / mean(observed kr/m²)` with `g` trained on *pooled* log kr/m² without location.
I tested it: because building age, floor, fee level and size correlate with location, a pooled `g`
carries location signal, which is then counted twice when multiplied by an area average. In the
omrade simulation it gives **MAPE 26.2 % (Jul–Aug) / 28.5 % (CV)** — worse than a constant. I
therefore train `g` on the *within-area* relative price:

```
y_i = log( price_per_sqm_i / mean price_per_sqm of the row's omrade )     (arithmetic mean, as in a published "average")
g   = LightGBM on y, features: boarea, antalRum, vaning, byggar, fee_per_sqm, 3 missing-indicators, hiss, balkong
      (no omrade, no postnummer);  150 trees, 15 leaves, lr 0.05
r(x) = clip( exp(g(x)) × smearing_factor / normaliser, clip_min, clip_max )
```

- **Normaliser = 1.0** by construction: every omrade's training rows have mean(price/omradeAvg)=1,
  so an average sale has r ≈ 1 and the published *average* (a mean, not a median) is the right
  multiplier. Measured: mean r over the 4,955 training rows = 0.9971 (smearing 1.01395).
- `general_model.json` carries `r_inference`: `smearing_factor` 1.013949, `normaliser` 1.0,
  `clip_min` 0.5029, `clip_max` 1.4440 (= min/max of r over training rows; trees cannot extrapolate,
  so the clip only matters as a documented bound), `mean_r_training_rows`, and `input_ranges_training`
  (min / p01 / p99 / max per input, so the UI can flag inputs outside the training range,
  e.g. boarea 16–245 m², fee 4.5–249 kr/m²).
- **Definition uncertainty:** Mäklarstatistik states "average" but not whether it is the mean of
  per-sale kr/m² or total price / total area. In our data these differ: mean of sale kr/m² = 91,655,
  total/total = 90,760, median = 90,741 (n=4,991, Jan–Aug 2026) — ≈ 1 %.
- **Obvious-direction guard:** unconstrained, `g` gave "no lift" a *+3.0 %* effect on r (confounding
  artefact; CLAUDE.md rule). `hiss` and `balkong` are therefore monotone-constrained
  (ja ↑, nej ↓) in `g`; r's marginal hiss effect is then 0.0 % and balkong −0.7 %, at no accuracy
  cost (simulated MAPE 14.48 vs 14.55 %). The OLS effect of "no lift" (−2.4 %) is *not* reproduced
  by `g`.
- **Transfer caveats (not testable with our data):** byggår shape (mean r 1.12 for 1915, 1.01 for
  1945, 0.92 for 1975, 0.96 for 2000, 1.02 for 2018) is a Stockholm pre-war premium; fee_per_sqm
  falls from r 1.06 (30 kr/m²) to 0.95 (90 kr/m²). Outside Stockholm both the premium pattern and
  the *absolute* fee level (which tracks regional costs) may differ. Without `fee_per_sqm`
  (`general_model_nofee.json`, same format, 779,202 B) the simulation costs +0.9 pp MAPE (below),
  but removes the absolute-fee transfer risk. **Open decision for the owner; default shipped = with fee.**

### Inputs to the regional method (data, not model)

`data/derived/regional_prisniva.json` (built by `ml/build_regional_prisniva.py` from the owner's
Svensk Mäklarstatistik xlsx, "uppdaterad 08 september 2026"): 26 kommuner + län (70,164 kr/m²) + Stockholm
reference (0180: 90,017 kr/m²), 12-month **average** (sep 2025 – aug 2026), **no n given**.
Riket 46,317 kr/m² is a **single month (aug 2026)** average from the owner (2026-10-07) — its period
differs from the kommun 12-month figures, so riket-based estimates mix periods.
Kommun for a postnummer: `data/derived/postnummer_kommun.csv` (see `ml/mapping/README.md`).
Postnummer without a kommun → no kommun average → national average (or no valuation; product decision).

**Exact regional formulas for TypeScript**

1. Inputs → booster vector as in §1 but **without** `omrade`, `postcode_delta` (order in
   `general_model.json.feature_order_out`; `hiss`/`balkong` one-hot; same imputation recipe).
2. `log_g = Σ_trees leaf(x)`; `r_raw = exp(log_g) × smearing_factor / normaliser`;
   `r = min(max(r_raw, clip_min), clip_max)`.
3. `kr_per_m2 = A × r`; `pris = kr_per_m2 × boarea`; interval `pris × exp(±q_regional)` with `q_regional = 0.2779`
   (metadata `regional_method.q_regional_log`). Confidence should always be low.
4. Parity: `general_parity_fixtures.json` (52 rows incl. 2 extreme boarea/fee rows) — reproduced to 1e-9 by the
   reference implementation in `test_valuation_v3.py`.
5. Product-side adjustment (TypeScript `rForPrissattning`, added after review 2026-10-08): the monotone
   constraint covers only the `ja`/`nej` one-hot columns, and `okant` priced up to +1.9 % above a confirmed
   lift. When `hiss` or `balkong` is `okant`, the r used for pricing is clamped between the r values of the
   known answers (all ja/nej combinations of the unknown attributes). Raw r (step 2) is unchanged and is what
   the parity fixtures check. The product also hides hiss/balkong drivers for these estimates, since r gives
   them no effect.

## Limitations

- No time feature (as v2). The regional method divides by an average valid for a 12-month window
  while our r(x) comes from Jan–Aug 2026.
- Postnummer encoding: 632 postnummer, thin per-postnummer evidence, probable building-level
  repeat-sale effect; unseen postnummer perform worse than without the feature (n=31).
- Tuning gain with the postcode feature is small (0.08 pp).
- Regional method: validated only by simulation inside Stockholm; true error elsewhere is unknown
  and likely larger. Average definition (mean of sales vs total/total) and the single-month riket figure
  are not verified against Mäklarstatistik's methodology.
- Okänt bucket (n=24, 35 % MAPE) unchanged.
